# Патерни з ревʼю ПР

Що повторюється в ПР до TAF і чого команді бракує, щоб писати за конвенціями з першого разу (P9). Джерело для T3-09 (playbook "як написати тест", шаблон) і для правил ревʼю: патерн, що трапився кілька разів, стає пунктом playbook або правилом гейта.

Правила:
1. Записуємо патерн коду, не людину: без імен і оцінок авторів.
2. Лише те, що має ціну (час прогону, флак, прихована регресія, зміна чужих тестів, дублювання); стиль не записуємо.
3. База: стан `origin/develop` на момент ревʼю, не цільовий канон вікі.
4. Повтор у новому ПР: додати номер у колонку "ПР", не новий рядок.

| ID | Патерн | Ціна | Як правильно на develop | ПР |
| --- | --- | --- | --- | --- |
| R-01 | Проба необовʼязкового елемента перед дією (`waitFor(...).then(() => true).catch(() => false)` + `if`), хоча тест знає, чи елемент буде | Без елемента повне очікування `actionTimeout` (60 с на develop) на кожен виклик; з коротким таймаутом флак; зникнення елемента маскується | Два методи без `if`, вибір у тесті за передумовою; `click` сам чекає появи. Умову показу брати з коду продукту | #162 |
| R-02 | Однакове тіло методу скопійоване в кожен підклас стратегії | Наступна зміна в N місцях (у #162 11 копій `closedDocument`) | Один конкретний метод у базовому класі над абстрактним `approvedDocument`; для фікстур налаштувань (у #202 4 майже однакові фікстури) одна функція-хелпер | #162, #202 |
| R-03 | UI-крок у шарі API-провізіонінгу (генерація API-токена через UI в company setup) | Падіння UI валить setup усього проєкту; page objects у менеджерах | Користувач через профіль, UI-крок у `beforeAll` спеки, де він потрібен | #162 |
| R-04 | Зміна поведінки спільного коду без згадки в описі ПР (формат дати в стратегіях, умова апруву, зміст параметра DB-хелпера) | Тихо змінює наявні тести; опис, згенерований CodeRabbit, цього не показує | Рядок в описі ПР і прогін наявних тестів, що викликають змінений код | #162 |
| R-05 | Форматування не прогнане (`prettier`, пробіли в кінці рядка) | Шум у диффі, конфлікти | `npm run format` перед пушем; з #203 це робить husky `pre-commit` | #162, #202 |
| R-06 | Точне `toBe` на результаті арифметики з грошима (`toBe(toPayBefore - partialAmount)`) | Порівняння float тримається, лише поки фікстура дає цілі ціни; з дробовою ціною, податком чи курсом не збігається приблизно третина сум (перебір 142 843 сум від 1.00 до 9 999.99: 35.9 %) — флак без дефекту | `toBeCloseTo(x, 2)` | #199 |
| R-07 | Булевий параметр-режим у методі дії (`addPaymentToInvoice(amount, false)` не додає платіж) | Назва методу бреше для одного з режимів; кожен новий режим додає `if` | Композиція: `fillPaymentAmount()` і `addPaymentToInvoice()`, що викликає його і підтверджує | #199 |
| R-08 | Пошук своїх даних циклом по пагінації спільного списку (`while (rows.count() === 0) next.click()`) | `count()` не чекає: якщо список ще вантажиться, цикл пропускає сторінку з потрібними даними; список росте із залишками попередніх прогонів, тест повільнішає з часом; не знайшовши, цикл мовчки виходить | Фільтр за своїм ідентифікатором (номер документа), далі `expect(rows).toHaveCount(n)` | #202 |
| R-09 | Негативна перевірка без позитивного якоря (`toBeHidden` / `not` одразу після переходу) | Проходить і тоді, коли блок ще не відрендерився: тест "не перенесено" зелений навіть при дефекті перенесення | Спершу перевірка, що сторінка готова (статус, заголовок), потім негативна | #202 |
| R-10 | Кроки й перевірки тесту не відповідають його назві (крок "друга позиція" діє через той самий локатор `rows.first()`, результат перевіряється лише для першої) | Тест зелений, навіть якщо друга позиція не оброблена; назва вводить в оману того, хто розбирає падіння | Явні `rows.nth(i)` або перевірка кількості після кожної дії; фінальна перевірка покриває все, що обіцяє назва | #202 |
