# Патерни з ревʼю ПР

Що повторюється в ПР до TAF і чого команді бракує, щоб писати за конвенціями з першого разу (P9). Джерело для T3-09 (playbook "як написати тест", шаблон) і для правил ревʼю: патерн, що трапився кілька разів, стає пунктом playbook або правилом гейта.

Правила:
1. Записуємо патерн коду, не людину: без імен і оцінок авторів.
2. Лише те, що має ціну (час прогону, флак, прихована регресія, зміна чужих тестів, дублювання); стиль не записуємо.
3. База: стан `origin/develop` на момент ревʼю, не цільовий канон вікі.
4. Повтор у новому ПР: додати номер у колонку "ПР", не новий рядок.

| ID | Патерн | Ціна | Як правильно на develop | ПР |
| --- | --- | --- | --- | --- |
| R-01 | Проба необовʼязкового елемента перед дією (`waitFor(...).then(() => true).catch(() => false)` + `if`), хоча тест знає, чи елемент буде | Без елемента повне очікування `actionTimeout` (60 с на develop) на кожен виклик; з коротким таймаутом флак; зникнення елемента маскується | Два методи без `if`, вибір у тесті за передумовою; `click` сам чекає появи. Умову показу брати з коду продукту | #162 |
| R-02 | Однакове тіло методу скопійоване в кожен підклас стратегії | Наступна зміна в N місцях (у #162 11 копій `closedDocument`) | Один конкретний метод у базовому класі над абстрактним `approvedDocument` | #162 |
| R-03 | UI-крок у шарі API-провізіонінгу (генерація API-токена через UI в company setup) | Падіння UI валить setup усього проєкту; page objects у менеджерах | Користувач через профіль, UI-крок у `beforeAll` спеки, де він потрібен | #162 |
| R-04 | Зміна поведінки спільного коду без згадки в описі ПР (формат дати в стратегіях, умова апруву, зміст параметра DB-хелпера) | Тихо змінює наявні тести; опис, згенерований CodeRabbit, цього не показує | Рядок в описі ПР і прогін наявних тестів, що викликають змінений код | #162 |
