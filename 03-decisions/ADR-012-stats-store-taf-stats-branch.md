# ADR-012: Статистика прогонів живе в гілці `taf-stats` репозиторію TAF у фіксованому форматі
Статус: superseded — [ADR-013](ADR-013-stats-store-aqa-stats-db.md), 2026-11-16 (тех. лід відмовив у токені на читання репо, сховище — БД AQA Stats)
Дата: 2026-10-26

## Контекст
Щоденний збір (`team_stats.py`, launchd о 12:00) працює на ноутбуці Євгена, а сховище (`~/Work/Precoro/stats`) локальний git без remote. Залежність від одного Mac: вимкнений ноутбук пропускає збір, Jenkins зберігає лише 31 нічну збірку, гілки зникають разом з історією.

Джерела прогонів множаться:
- нічний прогін у QA Jenkins (унікальне середовище з мікросервісами; джерело — Allure);
- гілкові прогони тепер у GitHub Actions продукту (`precoro/precoro`, workflow `PR Checks`); Allure там не вивантажується, джерело — лог Playwright (списки `failed` і `flaky`, помилка кожної спроби, `Slow test file`); dev Jenkins з 21.10 порожній;
- новий екшн «фіксова гілка → develop» з фулраном у TAF (будується окремо), теж має писати статистику.

Перевірено 26.10 на 92 логах Playwright-джобів продукту (22–26.10, 84 запуски, 56 гілок): лог містить проєкт, файл:рядок, назву, помилку кожної невдалої спроби для `failed` і `flaky`; кількість блоків помилок (230) дорівнює сумі `failed` (117) і `flaky` (113). Артефакт `playwright-report-*` живе 2 дні і лише при падінні; трейс знімається лише на останній спробі.

## Рішення
1. **Сховище** — окрема гілка `taf-stats` у репозиторії TAF без спільної історії з кодом (orphan). Дані туди пушаться напряму, без PR і без рев'ю; код збирача і workflow живуть у `develop` звичайним шляхом.
2. **Один файл на запуск, незмінний**: `data/<source>/<рік>/<id>-<attempt>-<suite>.json` (ключ запису; один запуск GHA може дати і smoke, і full). Паралельні записи не конфліктують, повторний запис ідемпотентний (існуючий файл пропускається).
3. **Формат — контракт**: `schema/v1.json` (JSON Schema) у цій же гілці. Усе, що потрапляє в `data/`, проходить валідацію (`jsonschema`, `pip install` кроком workflow; рішення 2026-10-29).
4. **Єдина точка запису** — скрипт `scripts/stats/write-run` у TAF: приймає запис, перевіряє проти схеми, робить checkout `taf-stats`, коміт, `pull --rebase`, `push` із повтором, під `concurrency`-групою. Пряме редагування `data/` вручну чи іншим кодом не передбачене.
5. **Дві форми надходження**: pull (збирач за розкладом забирає нічний із Jenkins) і push (екшн у TAF викликає `write-run` після свого прогону). Нове джерело = нова тека в `data/` і значення `source`. Уточнення 2026-10-29: гілкові прогони продукту (`precoro/precoro`, лог Playwright токеном лише на читання) у першому кроці не збираємо; вони додаються пізніше як ще одне джерело без зміни формату.
6. **Споживачі** читають лише `taf-stats`: розбір прогонів (екшн ранкового розбору нічного T0-30, статистика й флейки прогонів GHA), тижневі звіти й метрики (T0-14, weekly), дані сторінки-артефакта, будь-який інший внутрішній інструмент. Контракт — `schema/v1.json`; зведені показники не зберігаються, їх рахує споживач. Доступ приватний (репо закрите); якщо інструменту потрібен доступ, видається окремо, публічного URL не передбачено.
7. Сирі логи і трейси не зберігаються: лише розібраний запис (розмір і дані середовища).
8. **Три види записів** (рішення Євгена 2026-10-30), поле `kind`, схема `schema/<kind>-v<N>.json`: `run` (прогін), `debt` (щоденний знімок `scripts/debt.js` на `develop`, `data/debt/<рік>/<дата>-<sha8>.json`, з `definition_sha`: знімки з різним визначенням не порівнюються як ріст чи спад; ряд з 04.10.2026), `pr` (один запис на закритий PR, `data/pr/<рік>/<номер>.json`; відкриті споживач бере з GitHub). Пости Slack не збираються: причину не зеленого прогону дає `run.cause` (`tests` / `checkout` / `agent` / `aborted` / `setup` / `unknown`) з Allure і консольного логу Jenkins.

### Формат запису v1 (чернетка)
```
{
  "schema": 1,
  "source": "jenkins | full-run-taf",
  "run": { "id", "attempt", "url", "started_at", "duration_s", "event", "branch", "branch_kind", "pr"?,
           "sha", "suite", "conclusion", "env" },
  "totals": { "executed", "passed", "failed", "flaky", "skipped", "did_not_run", "machine_ms"? },
  "slow_files": [ { "project", "file", "duration_s" } ],
  "passed": [ "<test_id>", ... ],
  "tests": [ { "test_id", "qase_id", "project", "file", "line"?, "title", "started_at", "duration_ms", "ref"?, "status": "failed | flaky",
               "retries", "attempts": [ "<error_class>", ... ], "error" (перша невдала спроба, до 300 символів) } ]
}
```
- `source` — канал запису: хто зібрав, тека в `data/`, розділ у звітах. `jenkins` (нічний QA Jenkins, pull), `full-run-taf` (`full-run.yml` у TAF, push; будь-яка гілка, тип гілки в `run.branch_kind`). Далі можливий `full-run-precoro` (гілкові прогони продукту). `run.env` — стенд, окрема вісь: `qa` / `gha-taf`.
- `run.conclusion` — результат прогону за правилом `run-summary.js`: `failed`, якщо хоч один тест упав; flaky прогін не валить (їх видно в `totals.flaky` і `tests`). Значення: `passed` / `failed` / `aborted` / `no_tests`.
- `failed` включає Allure `broken` і Playwright `interrupted`; `test.fail`, що впав як очікувалось, рахується в `passed`.
- `title` — назва тесту з Playwright. У нічному Allure `name` для тестів з `allure.displayName` інша (77 викликів, 80 тестів з 2458 у збірці #297), тож збирач бере код на `sha` нічного і повертає справжню назву; інакше `test_id` нічного і GHA розійшовся б. `file` береться з мітки Allure `suite` (`fullName` інколи вказує на хелпер), слеші Windows нормалізуються.
- Qase ID у нічному Allure: крок `QaseID: <n>` верхнього рівня в `testStage.steps` кожного тесту (68 з 68 у вибірці #297, усі статуси), не мітка. У `suites.json` його нема: запит на тест, ≈ 2 хв на збірку у 8 потоків.
- `run-summary.js --json` вхідним форматом не є (лише лічильники і списки без помилок, часу, спроб і пройдених): `full-run-taf` читає `results.json` напряму.
- Історія починається з нічного #277 (sha `7c44a4ab`): у коді до #276 включно 80–83 тести мали кілька Qase ID в одній анотації, такі прогони не пишуться (рішення Євгена 2026-10-29), збирач пропускає прогін, де є хоч один такий тест. Збірки 277+ беруться з Jenkins. Мапінг `stats/raw` через `--list` (≈ 97%) не знадобився.
- Відсутні в джерелі `started_at` і `retries` тесту, `skipped` і `did_not_run` у `totals` — необов'язкові, відсутність означає «невідомо», не нуль; `attempts` може бути порожнім, якщо джерело не зберегло повідомлення.
- `tests` лише `failed` і `flaky` (з деталями); `passed` — стислий список `test_id` усіх пройдених без повтору. Разом вони дають **знаменник**: скільки разів тест виконувався, отже частоту флейків. Пропущені й не запущені лічаться в `totals`. Поля з `?` необов'язкові (нічний Allure не дає рядка).
- `test_id` = `<qase_id>:<hash8>`, де `hash8` — перші 8 символів sha1 назви тесту. Qase ID є на кожному тесті і не залежить від переносу файлів між компаніями, але ідентифікує **кейс**, а не окремий тест: параметризовані варіанти одного кейсу діляться id. Перевірено на реальному повному прогоні (`full-run.yml`, 2026-10-28, 1509 тестів): усі мають `QaseID` в анотаціях (відсутніх 0, нелітеральні місця теж), але унікальних id лише 1031; 197 id мають 675 тестів (45%), різняться назвами. Пара «Qase ID + назва» однозначна: 1509 з 1509, колізій 0. Тому ключ містить і хеш назви; поле `qase_id` пишеться окремо для групування варіантів одного кейсу. Зміна назви тесту рве ряд історії цього тесту (кейс лишається); перенос файлу чи компанії ряд не рве.
- `run.event`, `run.branch_kind` (`develop` / `fix` / `feature` / `other`), `run.pr`, `run.attempt`, `run.suite` (`smoke` / `full` / `nightly`), `run.sha` — для фільтрації: флейк на feature-гілці може бути регресією самої гілки, нічний іде на спільному стенді. Ключ запису: `run.id` + `run.attempt` + `run.suite`.
- `attempts` — клас помилки кожної спроби (для флейка перша спроба важливіша за фінальну).
- `started_at`, `duration_ms` — час падіння: потрібен розбору нічного для кластеризації за часом (падіння різних модулів в одному вікні → кандидат «стенд») і відкриття Grafana/Sentry на інтервал. `ref` — посилання на тест у джерелі (для нічного uid у Allure), щоб споживач міг дістати повну помилку й трейс, не шукаючи за назвою.
- Межа з розбором нічного (T0-30): розбір лише читає записи за цією схемою і ходить у Jenkins тільки по те, чого сховище не зберігає (повна помилка, кроки, трейс). Список впалих він з Jenkins сам не збирає.
- `error_class` — симптом (таймаут локатора, assertion, таймаут тесту, помилка API, помилка скрипта, інше), не причина.
- Обсяг: пройдені пишуться повністю. Виміряно на тому ж прогоні: сирий `results.json` 164 МБ (stdout і вкладення), стислий запис ≈ 41 КБ (1471 пройдений як `<id>:<hash8>` ≈ 29 КБ, 38 failed/flaky/skipped ≈ 12 КБ), ≈ 16 КБ після стиснення git. За ≈ 12 прогонів на добу (37 за 26–29.10, smoke менший за full) це порядку 60–100 МБ на рік. Зростання `taf-stats` дивимось за фактом, поріг перегляду визначимо тоді.

## Наслідки
- Збір не залежить від ноутбука; історія нічних більше не обмежена 31 збіркою.
- Нове джерело додається без зміни споживачів, якщо пише за схемою.
- Мова збирача: Python зі стандартною бібліотекою плюс `jsonschema` для валідації (рішення Євгена 2026-10-29); парсер Allure з `team_stats.py` переноситься в `scripts/stats/`. `team_stats.py` лишається, поки не збіглись показники.
- Гірше: потрібні права `contents: write` у workflow. Виняток для `taf-stats` у правилах захисту не потрібен (правила діють лише на `develop`, `dev`, `release`, `master`, `main`; перевірено 2026-10-29). Токен читання Actions у `precoro/precoro` знадобиться, коли додамо гілкові прогони продукту.
- QA Jenkins досяжний із раннерів GitHub (`ubuntu-latest` і blacksmith), вхід логіном і API-токеном працює, Allure нічного читається (проба 2026-10-29). Self-hosted раннер і push із самого нічного не потрібні.
- Різні середовища (нічний QA Jenkins і гілкові GHA) зберігаються разом, але в звітах лишаються окремими розділами за `source` (рішення 20.10: числа між ними не порівнюємо).

## Відхилено
- Окремий репозиторій для статистики: не погоджено.
- Коміти зі статистикою в `develop`: шум у журналі PR, `develop` захищений гейтом.
- Лише артефакти запусків: живуть 2 дні.
