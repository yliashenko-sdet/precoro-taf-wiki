# ADR-013: Статистика прогонів живе в БД сервісу AQA Stats, а не в гілці репозиторію
Статус: Draft
Дата: 2026-11-16
Замінює: [ADR-012](ADR-012-stats-store-taf-stats-branch.md)

## Контекст
ADR-012 поклав записи прогонів у гілку `taf-stats` репозиторію TAF. Сторінки AQA Stats (Nightly, Weekly, Metrics) живуть у сервісі `precoro/Sentry-Asana-webhook-integration` і мали читати цю гілку токеном GitHub. 13.11 тех. лід відмовив у токені на читання репо: репозиторій не місце для статистики, потрібна БД. Без читання Weekly не синхронізується, а заморожена гілка ламає історію ранкового розбору (T0-30).

## Рішення
1. Сховище — БД сервісу AQA Stats. Запис і читання через API сервісу: `POST /automation/api/taf-stats`, `GET …/paths`, `GET …/records`.
2. TAF шле записи скриптом `publish_stats.py` (замість `write_run.py`). Схеми записів лежать у `scripts/stats/schema/`, формат `run` / `debt` з ADR-012 зберігається.
3. Історію для розбору нічного TAF бере з сервісу (`fetch_records.py`), а не з гілки.
4. Тригер збору нічного з Jenkins лишається через `GITHUB_DISPATCH_TOKEN`: розклад GitHub відкладав запуски з 06:07 UTC на 13–14 UTC.
5. Наявні дані гілки переносить одноразовий backfill (`scripts/backfill_taf_stats.py` у сервісі).

## Наслідки
- Один власник даних — сервіс; токен на читання репо не потрібен, cron синхронізації в сервісі прибирається.
- Схема лишається контрактом, але живе в TAF, а не в гілці даних.
- Тех. лідові ще треба пояснити, навіщо лишається `GITHUB_DISPATCH_TOKEN`.

## Міграція
Порядок: сервіс (PR 330) мерджиться і деплоїться → backfill з Mac → TAF (#469) → прибрати `TAF_STATS_GITHUB_TOKEN` із `.env` сервісу. Задачі: T0-31, T0-30, T0-14; Asana «Перенести метрики AQA (nightly, weekly) у БД».

## Відхилені альтернативи
- Гілка `taf-stats` (ADR-012): потребує токена на читання репо, у якому відмовлено.
- Збір за розкладом GitHub Actions замість тригера з Jenkins: запуски запізнювались на 7–8 годин.
