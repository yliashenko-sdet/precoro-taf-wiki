# T0-30. Ранковий розбір нічного прогону в GitHub Actions
Asana: [[TAFMOD] T0-30. Ранковий розбір нічного прогону в GitHub Actions](https://app.asana.com/1/61124495704688/project/1218396784620561/task/1219879171332145), підзадача Part 1/3.
Біль: P1 (причини падінь важко дебажити), P8 (flaky), P17 (виправлення тестів серіалізує роботу): після нічного прогону причини падінь розбирає людина вручну, і розбір доходить далеко не до кожного падіння.

## Контекст
- Нічний прогін (QA Jenkins) дає десятки падінь (47 у #291 на `develop` 26.10), але вони зводяться до кількох причин: імпорт бюджетів 9 тестів з одним `toast:success`, Punchout 8 кліків, ICF/DCF Dependencies 4, глобальний таймаут тесту 6. Рахувати треба групи, не тести.
- Дані для розбору вже збираються: `team_stats.py` (`collect_nightly`) пише `raw/nightly/<n>.failures.json` (ключ, клас симптому, перші 300 символів `statusMessage`); класи `failure_class`: таймаут локатора, assertion, таймаут тесту, таймаут очікування, помилка API, помилка скрипта, інше. Клас береться з тексту повідомлення і є симптомом, не причиною.
- Розбір тредів гілок (T0-18, `01-context/jenkins-failed-builds.md` §8): продукт — 13% пояснених тестових падінь, тест не встиг за продуктом — 28%, flaky — 16%; половина падінь без розбору.
- QA Jenkins досяжний із раннерів GitHub (`ubuntu-latest` і blacksmith), вхід логіном і API-токеном працює, Allure і нічна збірка читаються (проба 2026-10-29). Секрети `JENKINS_*` і `ANTHROPIC_API_KEY` у репо є.
- Нічний Allure не містить логів продукту (лише сторона TAF і мережа браузера в трейсі); логи стеку є лише в гілкових прогонах `full-run.yml` (`docs/stack-logs.md`). Рішення 2026-10-29: стартуємо без них.

## Підхід
Частина 2а («використання: розбір прогонів») поверх ядра статистики. Залежить від T0-31 (ADR-012): екшн бере розібрані записи нічного з гілки `taf-stats`, а не парсить Jenkins сам; збір нічного і запис у сховище живуть у PR статистики, цей PR лише читає за схемою v1 і ходить у Jenkins по повну помилку й трейс. Окрема гілка і PR (поділ у T0-31, «Три частини»).

Етап 1 цієї задачі: лише звіт, без змін у тестах і без PR. Назва екшну і Check Run: **Precorino triage** (рішення Євгена 2026-10-29).

Логів стеку продукту на цьому етапі немає: за словами Максима, тести на Precorino рідко падають через помилки продукту, тож починаємо на даних TAF, трейсі й часі падінь. Логи додаємо, якщо вимір точності (крок 7) покаже, що категорії «стенд» і «продукт» без них недостовірні.

1. Workflow `precorino-triage.yml` у репо TAF: `cron` на ранок і `workflow_dispatch` з номером збірки; checkout коміту нічної збірки.
2. Збір і групування (детерміновано): записи нічного з `taf-stats`; група = клас симптому + нормалізований текст помилки + модуль; кластеризація за часом (падіння різних модулів в одному вікні → кандидат «стенд»); історія флейків групи з `taf-stats`.
3. Трейси (детерміновано, 1–2 репрезентативні тести на групу): `jenkins_fetch_traces.py fetch <job> <збірка> --filter <назва тесту>` зі скіла `playwright-trace-triage`, далі `analyze_trace.py --json`: вердикт, впала дія, хвіст логу Playwright, мережа ≥400, перехідність оверлея. Змінні скіла `JENKINS_USER` і `JENKINS_API_TOKEN` у workflow беруться з секретів `JENKINS_USER_NAME` і `JENKINS_PASS`, `JENKINS_URL` зі змінної. Фільтр за назвою, а не лише за Qase ID: варіанти одного кейсу ділять id (ADR-012). Для флейка потрібен трейс першої впалої спроби: перевірити, що нічний його зберігає і віддає. Тести без браузера (API) трейсу не мають, розбір лише за текстом помилки.
4. Розбір (судження Claude): на кожну групу окремий запуск із навичкою `playwright-trace-triage` (кроки 1–3 скіла: вердикт, тест чи застосунок; крок 4 дає пропозицію як diff, нічого не застосовуючи), права лише на читання, обмеження кроків і витрат; вихід JSON за схемою: категорія (тест, flaky, стенд, дані, продукт, невідомо), впевненість, докази, пропозиція, навчальний блок. Агентний запуск у чекауті (`claude-code-action` або CLI в headless-режимі) обирається за документацією на момент реалізації. Агент потрібен, коли пропозиція вимагає читання коду (знайти метод POM за селектором); для самої класифікації досить виводу `analyze_trace.py` і конвенцій, тож після першої ночі розглянути два рівні: класифікація прямим запитом, агент лише для груп, де потрібен diff (порівняти вартість і точність).
5. Перевірка (детерміновано): цитати з помилки й логу трейсу мають бути у вхідних даних, посилання на правила мають існувати (файл і розділ); без доказів категорія стає «невідомо».
6. Навчальний блок до кожної пропозиції (розбори роблять general QA з невеликим досвідом, тож звіт має вчити, а не лише казати «зроби так»): «як це визначили» (що дивитись у помилці й трейсі, по кроках), «чому так» (механізм причини простою мовою), «правило» (конкретний розділ `docs/test-conventions.md` або файл навички `playwright-best-practices`, конвенція Precoro зі скіла), «чого не робити» (антипатерн: фіксована пауза, `force: true`, порожній `catch`), «як перевірити самому». В анотації коротко, повний блок у `raw_details` анотації (звірити поле і ліміти) та в артефакті.
7. Звіт у GitHub Actions, окремим workflow (не `quality`, той лишається гейтом для PR):
   - Check Run «Precorino triage» через Checks API (право `checks: write`): одна анотація на групу, не на тест. Рівень за категорією: `error` продукт і невідоме, `warning` flaky і стенд, `notice` група з готовою пропозицією. Заголовок: категорія, модуль, кількість тестів. Текст: помилка, докази, пропозиція.
   - Прив'язка до місця в коді: `file` і `line` репрезентативного тесту з `playwright test --list --reporter=json` на коміті нічної збірки (Allure рядка не дає). Біля коду анотації видно лише в PR; нічний без PR, тож вони на сторінці запуску і в самій перевірці.
   - Job Summary: компактна таблиця «категорія → кількість»; повний звіт і diff-пропозиції артефактом запуску.
   - Ліміти (звірити з документацією перед стартом): workflow-команди `::error::` 10 на тип у кроці, Checks API 50 анотацій на запит.
8. Вимір точності: вердикти Claude звіряються з тим, що люди встановили самі (205 розібраних тредів Slack, PR фіксів, ніч #291 вручну); без цього етапи автофіксів і PR не починаються.

- Для однієї ночі (#291) Євген вручну перевірив вердикти по групах: частка правильних записана в картці.

- Навчальний блок перевірив хтось із general QA: зрозуміло, чому так і що робити самому (відгук записаний у картці).

## Ризики і залежності
- Право `checks: write` для workflow (локальне для репозиторію, нових секретів не потребує): підтвердиться першим запуском.
- Ключ Claude API є; ліміт витрат у консолі не виставлений (питання 37 у `07-open-questions.md`). Агентний запуск на групу дорожчий і менш передбачуваний за прямий запит: обмеження кроків і витрат на запуск, вимір вартості першої ночі.
- Нічний може не зберігати трейс першої впалої спроби флейка або не віддавати його через API: перевірити на реальному флейку до того, як на ньому тримається розбір.
- Скіл `playwright-trace-triage` написаний для інтерактивної роботи (`triage_qase.sh` логіниться через браузер); у CI використовується лише REST-шлях (`jenkins_fetch_traces.py`) і `analyze_trace.py`, вони без браузера.
- Клас симптому не причина: таймаут локатора може бути стендом, зміненим UI чи даними. Звіт так і подає.
- Автоматичний звіт позначений як згенерований; правило «без слідів AI» стосується комітів, гілок, PR, коментарів у репо; звіт у Job Summary читає лише команда, рішення про виняток за Євгеном.
- Автофікси і PR для нічних падінь поза цією задачею (етап 2: автофікси — [T0-37](../phase_2/T0-37.md), issues відповідальним — [T0-38](../phase_2/T0-38.md)). Ризик цього етапу: «адаптація» тесту під зміну може замаскувати реальну регресію; ловить це лише людина, що знає продукт. Правило «без підтвердженого прогону немає PR» також робить автоматичні PR без стенда неможливими.

## Відкинуто
- Одразу автоматичний PR із фіксами: не відповідає правилу прогону і не має виміряної точності розбору.
- Розбір по Slack-постах: половина падінь без треду, тож джерело неповне; Allure і трейси є завжди.
