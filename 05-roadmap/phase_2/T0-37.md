# T0-37. Автоматичні фікси простих нічних падінь (AQA Admin)

Етап 2 (рішення Євгена 2026-11-22). Фаза 0, продовження [T0-30](../phase_1/T0-30.md) (Precorino triage). ADR: —. Asana: —. Біль: P1, P8, P17.

## Біль

Precorino triage щоранку дає вердикт і пропозицію фіксу на кожну групу падінь. Сам фікс досі робить людина вручну, і до простих падінь руки доходять останніми, хоча фікс там механічний. Флейк із гонкою, зламаний локатор чи бракуюче очікування з ночі в ніч висять у звіті, поки хтось не знайде час.

## Що є зараз

- `precorino-triage.yml` (T0-30, done для етапу 1): групи, вердикт, докази, пропозиція, Assigned AQA з Qase (`scripts/triage/modules.py`). Змін у коді і PR не робить: в T0-30 це свідомо винесено за межі задачі.
- Скіл `daily-run-triage` (Максим, `15fdff6a`, 27.10; на `develop` з #449): розділ 3 дає вердикт на падіння і дію. Для «Test defect» це фікс у гілці, перепрогін і PR, для «Test data / time» — фікс передумови чи прибирання. Скіл написаний для інтерактивної сесії.
- GitHub App **AQA Admin** (Asana «Створити AQA admin app», закрита 17.11): встановлена лише на `precoro/precoro-e2e-playwright`, має лише право `Actions: Read and write`. Зараз вона запускає `stats-collect.yml` (`scripts/dispatch-stats-collect.js`).

## Що зробити

1. Відбір. Беремо лише групи з вердиктом flaky або test defect, тобто помилки коду тесту, з високою впевненістю і з доказами, які пройшли перевірку цитат. Логіку не чіпаємо: зміна очікуваного значення, кроку сценарію чи кейсу Qase означає логіку і йде людині. Product, стенд, дані, unknown і збій ночі (⚫) теж не беремо.
2. Фікс. На кожну відібрану групу окремий job: Claude зі скілом `daily-run-triage` (розділ 3, без кроків, що потребують VPN, БД dev чи коду продукту) робить гілку від коміту нічної збірки і мінімальний фікс у межах правил `CLAUDE.md` і `docs/test-conventions.md`. Обидва гейти `quality.yml` мають бути зелені.
3. Перевірка прогоном. Фікс без зеленого прогону не стає PR. Зачеплені тести проганяються через `full-run.yml` на Precorino кілька разів поспіль (для флейка більше, ніж для зламаного локатора; число фіксуємо на старті).
4. PR від імені AQA Admin. PR створюється як draft. Рев'ювер — Assigned AQA модуля з Qase. Тіло PR містить вердикт, докази, посилання на звіт ночі і на issue групи (T0-38). Auto-merge вимкнений, мерджить людина.
5. Обмеження: не більше N PR за ніч. Відкритий автоматичний PR на ту саму групу не дублюється, а отримує коментар про нову ніч. Вартість запуску записується в Job Summary.
6. Права App: додати `Contents: write` і `Pull requests: write`. Питання до власника App.

## Готово, коли

- Кілька ночей поспіль workflow відкриває PR на кожну відібрану групу, і кожен PR має зелений прогін зачеплених тестів.
- Жоден автоматичний PR не змінює очікування перевірки (перевіряє людина на рев'ю, ведеться облік).
- Частку PR, змерджених без правок, записано в картку.

## Метрика

- Частка автоматичних PR, змерджених без правок (з першого тижня).
- Час від нічного падіння до змердженого фіксу для простих груп: до і після.

## Ризики і залежності

- Головний ризик той самий, що в T0-30: «адаптація» тесту під зміну може замаскувати регресію. Тому відбір лише за flaky і test defect, заборона чіпати очікування, draft і рев'ю власника.
- Правило «без слідів AI» в комітах, гілках і PR. Автор тут бот AQA Admin, тож рішення, як підписувати такі PR, ухвалює Євген.
- Прогін на Precorino через GHA для фіксів спирається на `full-run.yml`; паралельні фікси не повинні заважати одне одному на спільних компаніях.
- Залежить від T0-38: PR посилається на issue групи.
