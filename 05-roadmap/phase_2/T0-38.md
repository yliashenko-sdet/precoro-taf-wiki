# T0-38. GitHub issues на відповідального за нічні падіння (AQA Admin)

Етап 2 (рішення Євгена 2026-11-22). Фаза 0, продовження [T0-30](../phase_1/T0-30.md) (Precorino triage). ADR: —. Asana: [Додати до результатів нічного тріажу створення github issues на відповідальних](https://app.asana.com/1/61124495704688/project/1133448714203913/task/1220495948920376) (з 13.11, без опису). Біль: P1, P17.

## Біль

Звіт Precorino triage читають, але він нікого не зобов'язує. Група падінь стоїть під Assigned AQA модуля лише в Job Summary. Хто взяв її в роботу, чи її вже полагодили і скільки ночей вона повторюється, видно лише з пам'яті людей.

## Що є зараз

- `precorino-triage.yml` (T0-30): групи зі сталим ключем (клас симптому + мішень + спека, `scripts/triage/group.py`), вердикт, докази, історія флейків за 15 ночей. Assigned AQA кожного тесту береться з кейсу Qase (`scripts/triage/modules.py`). Група стоїть під AQA, якому належить більшість її тестів.
- `scripts/triage/investigate.py` для масових і невідомих груп дає поле `owner`: чий це фікс (автор зміни, продукт, стенд).
- GitHub App **AQA Admin**: лише `Actions: Read and write`, тож права на issues ще нема.

## Що зробити

1. На кожну групу ночі одне issue, не на кожен тест. Issue створюється в `precoro/precoro-e2e-playwright` від імені AQA Admin.
2. Assignee — Assigned AQA групи з Qase. Мапа «користувач Qase → GitHub login» лежить файлом у репо; без логіна issue створюється без assignee з міткою `no-owner`.
3. Тіло issue: вердикт, докази, тести з QaseID і `file:line`, посилання на звіт ночі (Job Summary, сторінка Nightly run report) і на трейс.
4. Мітки ставляться за категорією вердикту і модулем.
5. Без дублів. У тілі issue стоїть прихований маркер із ключем групи. Якщо відкрите issue з тим самим ключем уже є, нова ніч додає коментар (номер збірки, скільки тестів) і нового issue не створює. Issue закриває людина або фікс-PR (T0-37, `Fixes #N`). Група, яка не повторювалась N ночей, отримує коментар про це, але сама не закривається.
6. Окремі випадки:
   - збій ночі (⚫) отримує одне issue з міткою `env`;
   - вердикт product отримує issue з міткою `product`, а рішення про задачу в Asana ухвалює AQA (за правилом скіла `daily-run-triage`).
7. Права App: додати `Issues: write`. Питання до власника App.
8. Запуск: як крок `precorino-triage.yml` після звіту. Режим `dry-run` (лише список issues у Job Summary) використовуємо, поки команда не погодиться.

## Готово, коли

- На реальній ночі на кожну групу створено одне issue з відповідальним або з міткою `no-owner`.
- Друга ніч з тими самими групами нових issues не створює, лише коментує наявні.
- Команда AQA погодилась на формат, і `dry-run` вимкнено.

## Метрика

- Частка груп ночі, що мають issue з assignee.
- Частка issues, закритих протягом тижня.
- Медіана ночей від першого падіння групи до закриття issue.

## Ризики і залежності

- Шум. Гучна ніч на 50 груп дає 50 issues. Тому одне issue на групу, коментарі замість дублів і окреме issue на збій ночі.
- Assigned AQA в Qase буває неправильним; його виправляють у Qase, як і для звіту T0-30.
- Відкрите питання 37: ліміту витрат на ключ Claude API нема. Ця задача викликів Claude не додає, бо працює на результатах розбору.
