# T1-45. Готовність сторінки: перевірка відкриття замість `waitForPageLoad`

Етап 2 (рішення Євгена 2026-11-22). Фаза 1, трек C. Codemod-и. ADR: —. Asana: [[TAFMOD] T1-45](https://app.asana.com/1/61124495704688/project/1133448714203913/task/1220765756315313), під Part 2/3. Додано в план 2026-11-19, привід — ревʼю PR #455 (`DashboardPage.gotoSupplierManagementPageUrl`).

## Біль

Методи переходу `goto*` / `open*` повертають новий page object, і жоден не перевіряє, що цільова сторінка відкрилась. Замість перевірки навколо переходу стоять очікування, які нічого не чекають:

```ts
// dashboard_page.ts, gotoSupplierManagementPageUrl
await this.waitForPageLoad();          // чекає сторінку, з якої йдемо
await this.waitForLoaderToDisappear(); // те саме; таймаут ковтається
await this.navigate(Constants.supplier_management_page_url);
await this.waitForPageLoad();          // дубль: navigate уже робить goto(..., { waitUntil: 'load' })
return new SupplierManagementPage(this.page);
```

`waitForPageLoad()` — це `waitForLoadState('load')`: на вже завантаженій сторінці повертається одразу. `navigate()` сам чекає `load`, обробляє перехоплену навігацію і пізній редірект. Тест, у якого перехід не вдався, падає не на переході, а пізніше, на першій дії по чужій сторінці, з незрозумілою причиною (той самий клас, що F-66: `waitForPageLoad()` після кліку Create, коли сторінка вже в стані «завантажено»).

## Що є зараз (develop `86099cc0`, 2026-11-19)

## Скоуп

**Входить:** PL з категорій A, B, C (≈ 202 виклики) і `expectOpened()` для 75 методів переходу.

**Не входить:** очікування лоадера (LD). Їх прибирають лише за виміром нічного прогону з `LOADER_INSTRUMENT` (T1-30 Part 2: статичне правило помилилось на 25 місцях, що наступної ночі показали лоадер); залишок — у T2-02. Категорія D (після кліку) — по місцю, разом із заміною на web-first перевірку результату, не codemod-ом.

## Що зробити

1. Метод `expectOpened()` на сторінках, куди ведуть `goto*` / `open*`: web-first `expect(<елемент, що є лише на цій сторінці>).toBeVisible()`, локатор у `*_locators.ts`, test-id першим. Якір обирати за trace, не за назвою.
2. Методи переходу: `navigate(url)` → `new XxxPage(this.page)` → `await xxxPage.expectOpened()` → `return`. PL до і після `navigate` прибрати.
3. PL категорії C прибрати codemod-ом за списком `file:line` з аудиту (ідемпотентно).
4. Прогнати зачеплені спеки до і після (`affected-tests`), починаючи з `dashboard_page.ts`.
5. Показник `waitForPageLoad calls` у `debt.js` (без гейта до кінця задачі; гейт — коли решта PL обґрунтована).

Окремий метод-обгортку для пари `waitForPageLoad` + `waitForLoaderToDisappear` у `BasePage` не робити: він узаконить шум у ~105 парах і ускладнить прибирання.

## Ризики

- Неправильний якір `expectOpened()` (елемент, що є і на попередній сторінці) дасть хибно-зелений перехід: якір перевіряти на trace переходу.
- Сторінки з редіректом (немає доступу, 403): `expectOpened()` там, де тест чекає відмову, не викликати; такі методи (напр. `expectSupplierManagementPageClosed`) перевіряють відмову окремо.
- `refreshBrowser` у циклах retry (`base_document.ts:1259`, `rfp_page.ts:279`): PL там частина кроку, перевіряти по місцю.

## Готово, коли

Кожен `goto*` / `open*`, що повертає page object, закінчується `expectOpened()` цільової сторінки; PL перед і після `navigate` / `goto` і на початку методів без навігації — 0; зачеплені спеки прогнані до і після без нових падінь.

## Метрика

`goto*` / `open*` без перевірки готовності: 75 → 0; PL категорій A+B+C: ≈ 202 → 0; `waitForPageLoad` усього: 335 → (виміряти після).
