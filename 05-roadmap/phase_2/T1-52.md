## Біль

API-тести запису збирають тіло запиту прямо у виклику клієнта, з окремих змінних (`const item_price = 99.99; … addItem({ price: item_price, … })`). Після відповіді вони перевіряють лише статус і схему: чи збереглось те, що надіслали, тест не дивиться. Щоб додати таку перевірку, ті самі значення доводиться збирати вдруге, вже для `expect`. Межі між підготовкою, дією і перевіркою в тексті тесту не видно.

## Що зробити

1. **Arrange.** Тіло запиту — один об'єкт `payload`, зібраний до виклику. Випадкові значення генеруються тут же.
2. **Act.** Клієнт отримує саме `payload`, без перезбирання полів у виклику.
3. **Assert.** Статус, `expectSchema`, потім `toMatchObject` проти очікуваного, зібраного з `payload`. Поля, що в запиті й відповіді мають різну форму, перекладаються явно (`supplier_id` → `supplier: { id }`, число → рядок, де відповідь віддає рядок), поля, яких у відповіді немає, виймаються через `const { field, ...rest } = payload` з коментарем чому.
4. Записати правило в `docs/test-conventions.md` і шаблон `docs/templates/test_example.spec.ts.txt`, щоб нові тести (T1-27, T1-48) писались одразу так.
5. Переписувати порціями за модулями, у файлах модулів з T1-47.

## Ризики

- Порівняння з надісланим знаходить розбіжності, які зараз мовчать: поле, яке бекенд ігнорує, або формат, що повертається інакше. Кожна така — або баг бекенду (у список для розробників), або виправлення очікуваного в тесті з поясненням. Тест не підганяється під відповідь мовчки.
- `test_api.spec.ts` чіпають ще T1-47 (розбиття), T1-50 (snake_case → camelCase, 572 порушення в цьому файлі) і T1-51 (тіло без незаданих полів). Порядок: T1-47 спершу, далі ця задача по файлах модулів; T1-50 у тих самих файлах — після неї, щоб не переписувати двічі.

## Готово, коли

Кожен тест запису в API-спеках будує `payload`, відправляє його і порівнює відповідь з ним (або з документом-джерелом, як repeat); поділ Arrange / Act / Assert; правило в `docs/test-conventions.md` і в шаблоні; зачеплені спеки прогнані до і після, кожна знайдена розбіжність розібрана.

## Метрика

Тестів запису, що порівнюють відповідь з надісланим: 0 з 58 (`3ad857a6`) → 58 з 58; з `payload` і Arrange / Act / Assert: 0 → усі тести запису. Розбіжностей, знайдених порівнянням, — окремий список (баги бекенду або виправлені очікування).
