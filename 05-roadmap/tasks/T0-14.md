## Підхід
Щотижня (понеділок) workflow в GitHub Actions, `cron` з `develop`:
1. Техборг: `npm run debt` на двох комітах (початок і кінець тижня), дельта по кожному показнику; джерело кожної цифри це запуск скрипта на названому коміті.
2. Показники прогонів із `taf-stats` за тиждень: стабільність нічного (частка падінь, масові ночі окремо), флейки (кількість, нові, найчастіші за кейсом: `passed` дає знаменник), класи падінь, тривалість, прогони TAF; джерело кожної цифри це запис зі `id` запуску й посиланням.
3. Доставка: короткий підсумок у Slack (дельти й головні рухи), повний звіт файлом `metrics/weekly/YYYY-Www.md`.
4. Після збігу показників за тиждень вимикається `team_stats.py` і його щоденний запуск (разом із T0-31).

## Готово, коли
- Звіт приходить у Slack щопонеділка; числа техборгу збігаються з `npm run debt` на тих самих комітах.
- Числа прогонів збігаються з ручним підрахунком за записами `taf-stats` і з `team_stats.py` за ті самі дні.
- На тести не впливає: підтверджений прогін не потрібен (у тілі PR написати чому).

## Відкриті питання
- Slack: канал, формат повідомлення, вебхук чи бот-токен (секрет у репо додає адмін).
- Де лежить повний звіт: `taf-stats` (пишемо без PR) чи `develop` (захищений, потрібен PR).
- Machine-time (час загалом і на тест, top-5 прискорень і сповільнень по проєктах, top movers серед тестів): запис v1 має лише `totals.machine_ms?` і `slow_files`. Або брати з `metrics-reporter` (його треба запускати в CI), або додати час по проєктах чи по тесту в запис v1.
- Залежить від T0-31.
