# T0-30. Ранковий розбір нічного прогону в GitHub Actions
Asana: [[TAFMOD] T0-30. Ранковий розбір нічного прогону в GitHub Actions](https://app.asana.com/1/61124495704688/project/1218396784620561/task/1219879171332145), підзадача Part 1/3, дедлайн 2026-10-27.
Біль: P1 (причини падінь важко дебажити), P8 (flaky), P17 (виправлення тестів серіалізує роботу): після нічного прогону причини падінь розбирає людина вручну, і розбір доходить далеко не до кожного падіння.

## Контекст
- Нічний прогін (QA Jenkins) дає десятки падінь (47 у #291 на `develop` 26.10), але вони зводяться до кількох причин: імпорт бюджетів 9 тестів з одним `toast:success`, Punchout 8 кліків, ICF/DCF Dependencies 4, глобальний таймаут тесту 6. Рахувати треба групи, не тести.
- Дані для розбору вже збираються: `team_stats.py` (`collect_nightly`) пише `raw/nightly/<n>.failures.json` (ключ, клас симптому, перші 300 символів `statusMessage`); класи `failure_class`: таймаут локатора, assertion, таймаут тесту, таймаут очікування, помилка API, помилка скрипта, інше. Клас береться з тексту повідомлення і є симптомом, не причиною.
- Розбір тредів гілок (T0-18, `01-context/jenkins-failed-builds.md` §8): продукт — 13% пояснених тестових падінь, тест не встиг за продуктом — 28%, flaky — 16%; половина падінь без розбору.
- QA Jenkins хост резолвиться в публічну адресу (з машини Євгена, 26.10); досяжність із раннерів GitHub не перевірена.

## Підхід
Залежить від T0-31 (ADR-012): екшн бере розібрані записи нічного з гілки `taf-stats`, а не парсить Jenkins сам; кроки 1–2 нижче переходять у T0-31.

Етап 1 цієї задачі: лише звіт, без змін у тестах і без PR.
1. Workflow `nightly-triage.yml` у репо TAF: `cron` на ранок і `workflow_dispatch` з номером збірки. Береться остання повна нічна збірка через Jenkins API.
2. Збір: впалі тести з Allure, текст помилки, клас симптому; групування за однаковою причиною (клас + нормалізований текст помилки + модуль).
3. Розбір Claude по групах: категорія (тест, flaky, стенд, дані, продукт), докази, пропозиція фіксу як diff у звіті, якщо причина однозначна; для сумнівних груп `trace.zip` (скіл `playwright-trace-triage`), якщо нічний його зберігає.
4. Звіт у GitHub Actions, окремим workflow (не `quality`, той лишається гейтом для PR):
   - Check Run «Nightly triage» через Checks API (право `checks: write`): одна анотація на групу, не на тест. Рівень за категорією: `error` продукт і невідоме, `warning` flaky і стенд, `notice` група з готовою пропозицією. Заголовок: категорія, модуль, кількість тестів. Текст: помилка, докази, пропозиція.
   - Прив'язка до місця в коді: `file` і `line` репрезентативного тесту з `playwright test --list --reporter=json` на коміті нічної збірки (Allure рядка не дає). Біля коду анотації видно лише в PR; нічний без PR, тож вони на сторінці запуску і в самій перевірці.
   - Job Summary: компактна таблиця «категорія → кількість»; повний звіт і diff-пропозиції артефактом запуску.
   - Ліміти (звірити з документацією перед стартом): workflow-команди `::error::` 10 на тип у кроці, Checks API 50 анотацій на запит.
5. Вимір точності: вердикти Claude звіряються з тим, що люди встановили самі (треди, PR фіксів); без цього етапи автофіксів і PR не починаються.

Скрипт розбору детермінований там, де можна (збір, групування, класи), Claude лише там, де потрібне судження (категорія, пропозиція).

## Готово, коли
- Workflow проходить на реальній нічній збірці з GitHub Actions; звіт читається за хвилину.
- Для однієї ночі (#291) Євген вручну перевірив вердикти по групах: частка правильних записана в картці.
- Секрети (Jenkins, ключ Claude API) лише в GitHub Secrets; у логах і звіті їх нема.

## Ризики і залежності
- Досяжність QA Jenkins із хмарних раннерів: якщо він за VPN чи allowlist, потрібен self-hosted раннер (питання до Максима).
- Право `checks: write` для workflow (локальне для репозиторію, нових секретів не потребує).
- Секрети в репо додає адмін репозиторію (`avramch`, через Олександра); ключ Claude API відкритий (питання 37 у `07-open-questions.md`).
- Клас симптому не причина: таймаут локатора може бути стендом, зміненим UI чи даними. Звіт так і подає.
- Автоматичний звіт позначений як згенерований; правило «без слідів AI» стосується комітів, гілок, PR, коментарів у репо; звіт у Job Summary читає лише команда, рішення про виняток за Євгеном.
- Автофікси і PR для нічних падінь поза цією задачею. Ризик цього етапу: «адаптація» тесту під зміну може замаскувати реальну регресію; ловить це лише людина, що знає продукт. Правило «без підтвердженого прогону немає PR» також робить автоматичні PR без стенда неможливими.

## Відкинуто
- Одразу автоматичний PR із фіксами: не відповідає правилу прогону і не має виміряної точності розбору.
- Розбір по Slack-постах: половина падінь без треду, тож джерело неповне; Allure і трейси є завжди.
