# Codemod і контрольний показник

## Що таке codemod

Скрипт, що робить одну правку в сотнях файлів через синтаксичне дерево, не через текст. Інструмент: TypeScript compiler API (`typescript` уже в залежностях репо), він дає і синтаксичне дерево, і типи. Розуміє структуру: "виклик `expect` з аргументом `await x.isVisible()` і далі `.toBe(true)`" переписується цілком, а схожі рядки з іншим змістом не чіпаються.

## Коли codemod, коли руки

| Патерн | Спосіб |
| --- | --- |
| `allure.step` → `test.step`, `attachment` → `attach` | codemod |
| `expect(await x.isVisible()).toBe(true)` → `await expect(x).toBeVisible()` | codemod |
| `waitForTimeout(N)` перед `expect` → видалення | codemod + прогін |
| `Constants.x` → `config.x` | codemod |
| snake\_case → camelCase | codemod (rename через ts-morph, безпечно) |
| `'{}'` + `.replace('{}')` → функція-локатор | codemod |
| `.catch(() => false)` поза предикатами | codemod знаходить, видаляє порціями, прогін підтверджує |
| `force: true`, `clickUsingJavascript` | руки: список від codemod, рішення людини |
| UI-логін → `asUser` | codemod для типового випадку, руки для решти |

## Борг, що залежить від поведінки продукту: instrument + nightly run
Force-кліки, `catch`-ковтання, sleeps не можна замінити наосліп: невідомо, що кожен прикриває. Але й ревʼю по одному не потрібне. Підхід:
1. Хелпер отримує інструментований fallback: спершу штатний виклик із коротким таймаутом, при невдачі стара поведінка плюс запис у лог (тест, локатор, причина від Playwright).
2. Прямі виклики (`force: true`, `dispatchEvent`, `waitForTimeout`) кодмодом заводяться через той самий хелпер.
3. Один нічний прогін дає список: де fallback не спрацював жодного разу (кодмод на штатний виклик без ризику) і де спрацював, згруповано за причиною.
4. Кластери закриваються спільним рішенням: "intercepts pointer events" через обробку накладок (T1-21), "not stable" через очікування, "not visible" через скрол або дефект продукту.
5. Те, що лишилось, отримує коментар-причину і живе легально.

Аргумент: actionability у Playwright це погляд користувача; force це "натисни, навіть якщо користувач не зміг би". Частина таких місць прикриває дефекти продукту, і їх треба розкрити, а не зберегти.

## Як робити codemod: покроково

Зібрано з T0-02, T0-13, T1-12, T1-13 (2026-09-24 – 10-02).

1. **Крок 0, картка.** Перевірити картку задачі на актуальність або написати її; цифри знімаються заново на поточній базі.
2. **Сухий запуск до правок.** Скрипт на TypeScript API (`typescript` уже в залежностях репо; `ts-morph` не потрібен) класифікує кожне входження за формою і типом операнда і друкує групи з кількістю. Групи й цифри йдуть у картку, рішення по кожній групі приймає Yevhen до запуску з `--write`. Приклад: `eqeqeq` у T0-02 розклався на "тип точний / перевірка мертва / тип `unknown`".
3. **Скрипт змінює лише однозначне.** Решту він виписує списком з причиною, і ці місця правляться вручну окремо. Якщо тип нічого не гарантує (`unknown`, дані з БД і API), поведінку не змінювати.
4. **Повторюваність.** Скрипт ідемпотентний і запускається на будь-якій гілці: при конфлікті з `develop` чи з гілкою General QA не резолвити руками, а взяти їхню версію і запустити скрипт заново (`working-agreement.md`, "Гілки, коміти, PR" і "Перебудова човна на ходу"). Codemod, що лишається в репо, лежить у `scripts/codemod-<тема>.js` (Node, як решта `scripts/`); одноразовий може жити поза репо.
5. **Після запуску.** `tsc`, `npm run lint`, `npx prettier --write` на змінених файлах, `npm run debt:check`; прочитати діф. Зміни поведінки (додали `await`, перевірка стала справжньою) перелічити окремо в картці й в описі PR.
6. **Знахідки поза скоупом** (дефект `F`, спрощення `I`) не виправляються в задачі, а йдуть у `01-context/findings.md`.
7. **Гейт.** Коли codemod вводить заміну для патерну, той самий PR вмикає для нього `gated: true` у `scripts/debt.js`; якщо лічильника ще нема, PR його додає. Лічильник терпить переноси рядків (Prettier), а коли регулярки замало, рахує через AST; кожен лічильник має приклади в самоперевірці (`npm run debt -- --self-test`). Правило гейта і перелік: картка T0-13.
8. **Lint, коли патерн прибрано повністю.** Тоді гейт для нього можна замінити lint-правилом `error` на весь репо, як `waitForTimeout`.
9. **Прогін.** Codemod, що змінює поведінку, перевіряє один повний локальний прогін на хості з порівнянням із базою «до» (`06-playbooks/local-run.md`); тести, що локально не біжать, назвати в описі PR. Без прогону поведінкова зміна не мержиться.
10. **Коміт і PR** за `working-agreement.md`: зміни незакомічені до "так" Yevhen, одна задача = один коміт.

## Контрольні показники: `scripts/debt.js`

- `npm run debt`: таблиця всіх показників на поточному коміті; одиниця: входження в коді без коментарів. Цифри не зберігаються: "до і після" це запуск на двох комітах.
- `npm run debt:check`: гейт. Для кожного зміненого файлу патернів з переліку гейта не більше, ніж у `develop`; новий файл рахується від 0, перейменування порівнюються зі старим шляхом.
- На GitHub (крок Debt check у `quality.yml`): анотація на кожному доданому рядку, що приніс патерн з гейта, і таблиця "develop / PR" по змінених файлах у Summary запуску.
- Під гейтом на 2026-10-02 (PR #203): `waitForTimeout`, `.catch(() => {})`. T1-12 і T1-13 додають свої патерни у своїх гілках; `debt.js` там уже відійшов від версії в гейті: при зведенні брати їхні лічильники, а вивід (анотації, Summary) з гейта.
